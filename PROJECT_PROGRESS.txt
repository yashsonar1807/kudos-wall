Risks, Dependencies & Mitigations:
1. Point Transfer Race Conditions:
   - Risk: Simultaneous requests could cause negative balance or double spending.
   - Mitigation: Use MongoDB multi-document transactions (session.startTransaction()) or atomic conditional updates ($inc with $gte guard).
2. Refresh Token Theft / Replay:
   - Risk: Stolen token reused by an attacker.
   - Mitigation: Store token hash in DB, rotate token on every /refresh, invalidate token family if an old token is reused, deliver strictly via httpOnly cookies.
3. Coss UI Primitive Availability:
   - Risk: External commercial package dependency.
   - Mitigation: Implement clean, accessible Coss UI primitives directly in frontend/src/components/ui/ using native CSS variables.
4. Aggregation Query Performance:
   - Risk: Slow leaderboard queries as feed scales.
   - Mitigation: Create compound database indexes on createdAt, recipient, department, and points.

OPERATION 3: Dual-Token Auth System & Security Middleware
--------------------------------------------------------------------------------
Objective:
- Build complete dual-token authentication system with short-lived JWT Access Token (15m) and long-lived Refresh Token (7d).
- Deliver tokens securely via httpOnly cookies.
- Support optional Authorization Bearer header for flexibility with external API clients and testing.
- Implement Refresh Token Rotation and proactive Replay Attack Detection.
- Implement email verification simulation.
- Enforce strict server-side validation, password hashing, and error response envelopes.

Authentication Architecture:
- Client (Browser) <--> httpOnly Cookies (accessToken: 15m, refreshToken: 7d) <--> Express Server
- Stateless Access Token verification on every protected request via JWT secret.
- Stateful Refresh Token validation via MongoDB RefreshToken collection with SHA-256 hashing.
- Token Rotation on renewal: old token revoked with lineage pointer; new token issued.
- Replay Detection: Re-use of a revoked token triggers instant revocation of ALL tokens for that user family.

Auth API Endpoints:
1. POST /api/auth/signup:
   - Body: { name, email, password, department, [avatar] }
   - Validation: name (2-50 chars), valid email regex, password >= 8 chars, valid department enum.
   - Behavior: Rejects duplicate emails with 409 Conflict. Generates simulated email verification token. Hashes password with bcrypt. Sets httpOnly accessToken and refreshToken cookies. Returns 201 Created with sanitized user object and verification simulation instructions.
2. POST /api/auth/verify-email:
   - Body: { email, token }
   - Behavior: Hashes candidate token with SHA-256, matches against stored hash, verifies expiry (< 24h). Sets isEmailVerified: true and clears verification tokens. Returns 200 OK.
3. POST /api/auth/resend-verification:
   - Body: { email }
   - Behavior: Generates new 32-byte crypto verification token, updates user, returns simulation details.
4. POST /api/auth/login:
   - Body: { email, password }
   - Behavior: Finds user (+password), compares with bcrypt. Returns 401 with uniform message on failure to prevent username enumeration. On success, generates 15m access token + 7d refresh token with random jti salt, stores SHA-256 hash in DB, sets httpOnly cookies, returns 200 OK with sanitized user.
5. POST /api/auth/refresh:
   - Source: Reads refreshToken from httpOnly cookie (fallback to request body).
   - Behavior: Verifies token existence, matches SHA-256 hash in DB. If revoked, triggers REPLAY ATTACK DEFENSE (invalidates all active sessions for user, returns 403 Forbidden). If valid, rotates token (revokes old, issues new pair with jti salt), sets updated httpOnly cookies, returns 200 OK.
6. POST /api/auth/logout:
   - Source: Reads refreshToken from cookie/body.
   - Behavior: Marks token revoked: true in MongoDB, clears accessToken and refreshToken cookies with matching path/domain options. Returns 200 OK.
7. GET /api/auth/me:
   - Middleware: protect
   - Behavior: Verifies access token from httpOnly cookie or Authorization Bearer header, loads active user from DB, returns user profile, department, and recognition wallet allowances. Returns 401 if missing/invalid/expired.

Cookie and Token Behavior:
- Cookie Name: 'accessToken'
  * Expiry: 15 minutes (maxAge: 15 * 60 * 1000)
  * Flags: httpOnly: true, path: '/', sameSite: 'lax' ('strict' in prod), secure: (NODE_ENV === 'production')
- Cookie Name: 'refreshToken'
  * Expiry: 7 days (maxAge: 7 * 24 * 60 * 60 * 1000)
  * Flags: httpOnly: true, path: '/', sameSite: 'lax' ('strict' in prod), secure: (NODE_ENV === 'production')
- Global uniqueness: All refresh tokens embed a 16-byte random hex 'jti' payload claim preventing identical token strings and duplicate hash collisions during rapid consecutive calls.

Security Measures:
- Passwords hashed with bcryptjs (12 salt rounds); select: false prevents leakage in queries.
- Password hashes and reset/verification tokens stripped via toJSON/toObject schema transforms.
- Refresh tokens hashed with SHA-256; plaintext tokens never persisted in database.
- Refresh token replay attack protection invalidates entire user token family on breach detection.
- Secrets loaded strictly via process.env with safe development defaults; zero secrets hardcoded.
- Helmet security headers and CORS origin checking enabled.
- Authorization checks enforced strictly on server side; no reliance on client state.
